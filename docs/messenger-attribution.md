# Подтверждённые входы в мессенджер из Директа

Сайт связывает рекламный переход с получением `/start ad_<метка>` ботом Telegram или `bot_started` с этой меткой ботом MAX. Это **подтверждённый вход в бота**, а не клик по кнопке сайта, не установка приложения, не новый пользователь и не первая запись. Одному человеку в одном мессенджере засчитывается не более одного такого входа за московский день. Повтор webhook и повторное использование одной ссылки не добавляют конверсию.

## Что уже делает код

- На лендинге получает ClientID Метрики через `getClientID` (cookie `_ym_uid` — запасной путь) и `yclid` из рекламного URL. Идентификаторы остаются строками, без округления больших чисел.
- Сохраняет их в Redis на 10 дней. В ссылке на мессенджер — только случайная 32-символьная метка. При новом `yclid` создаёт новую привязку.
- Передаёт эту же метку в QR-ссылку `/open?ref=...`. При сканировании на телефоне сохраняется рекламный переход с компьютера.
- Подтверждает конверсию только в обработчике проверенного webhook мессенджера. Исключение владельца совпадает с существующим `analyticsQuiet`.
- Атомарно сохраняет событие и очередь отправки в Redis до ответа webhook. Затем загружает CSV в Метрику. При ошибке очередная попытка — на следующем подтверждённом входе, при почасовом `/api/telegram/digest` или при ручном POST `/api/acquisition/sync`.
- При сбое аналитики переход в бот и его ответ продолжают работать. Без идентификаторов рекламная атрибуция невозможна: приложение не подставляет случайный ClientID и не считает нажатие на сайте запуском.
- Ранний клик до загрузки JavaScript проходит через `/go/telegram` или `/go/max`: сервер берёт `_ym_uid` и `yclid` из своего referer. Если их ещё нет, бот откроется без привязки.
- Статический QR остаётся запасным вариантом, пока Метрика и персональная QR-ссылка не загрузились. Такой ранний QR не связывается с исходным компьютером.

В Яндекс уходят только `ClientId`, `yclid`, `Target`, `DateTime`. Имя, ID мессенджера, заметки, чувства и переписка не передаются. Сервер использует HMAC пользователя только для внутренней защиты от повторов, с TTL 10 дней. Связка рекламного визита с техническим событием запуска описана в разделе 8.3 политики сайта на всех 12 языках.

## Включение в Метрике и Директе

1. На счётчике **114026277** 14 ноября 2026 уже созданы и проверены в интерфейсе две цели типа **«Целевое событие»**, условие — точное совпадение:
   - «Подтверждённый вход в Telegram» — идентификатор `messenger_start_telegram`, ID цели **681743373**.
   - «Подтверждённый вход в MAX» — идентификатор `messenger_start_max`, ID цели **681744319**.
   Повторно создавать их не нужно. События на сайте через `reachGoal` для этих целей не вызываются.
2. Получить OAuth-токен с правом `metrika:offline_data` для владельца/представителя этого счётчика. Этот доступ позволяет загружать офлайн-данные и достаточен для интеграции; более широкий `metrika:write` не нужен. Сохранить **только на сервере** в переменной окружения Vercel `METRIKA_OAUTH_TOKEN`. Не использовать `NEXT_PUBLIC_`, не коммитить и не отправлять токен в чат.
3. Развернуть версию с этими изменениями. Сохранить существующий почасовой запуск `/api/telegram/digest` с заголовком `Authorization: Bearer <CRON_SECRET>` — он также повторяет загрузку очереди. Новый публичный источник CSV с секретом в URL не создаётся.
4. Выполнить один реальный переход с рекламного URL на сайт и запуск бота с **отдельного тестового аккаунта**, который не исключён как владелец. Тестовая конверсия попадёт в отчёт; учитывать её отдельно при оценке рекламы. Свои запуски владельца должны по-прежнему пропускаться.
5. Проверить состояние через авторизованный `GET /api/acquisition/sync`. Ответ содержит `configured`, `pending`, `lastUpload`. `uploaded` и `uploadId` означают только приём файла API. **Это ещё не успешная привязка к визиту.** Долю привязанных конверсий проверить в настройках счётчика → загрузка данных; причины ошибок — в отчёте офлайн-конверсий.
6. После обработки добавить новые цели в столбцы отчёта Директа. Текущую стратегию, бюджет и кнопочные цели код не меняет. Решение об оптимизации на новую цель принимать после проверки её доставки и качества.

Без OAuth события сохраняются в очереди, но не отправляются. Первые загрузки возможны только для ещё не истёкших записей. Старые клики/пользователи до установки привязки задним числом не восстанавливаются.

## Ограничения и эксплуатация

- Для проверки со своего аккаунта можно временно задать серверную переменную `METRIKA_OWNER_TEST_UNTIL` с точным ISO-временем окончания, например `2026-11-15T01:45:00+03:00`, и развернуть новую версию. До этого момента исключение владельца отключается только для этих двух целей Метрики; PostHog и `/stats` продолжают исключать владельца. При наступлении срока исключение возвращается автоматически без нового развёртывания. Пустое, неверное или прошедшее время не включает тест. Повторы по-прежнему отсеиваются. Тестовые конверсии попадут в обычные цели и должны учитываться отдельно при оценке рекламы.

- Реальные запуски без рекламной метки не экспортируются. Прямой запуск Mini App из каталога, старый чат, сторонняя ссылка и просмотр профиля бота не являются этой конверсией. Бот должен получить команду/событие запуска с меткой.
- Один человек в Telegram и MAX считается отдельно. Повторные рекламные входы в последующие дни возможны; это показатель входов, а не уникальных новых клиентов.
- Очередь обрабатывается порциями до 50 записей. При большем потоке настроить отдельный регулярный POST `/api/acquisition/sync` с тем же Bearer-заголовком. GET показывает состояние и ничего не загружает.
- При транспортном обрыве после приёма файла Яндексом локальный результат может быть неизвестен. Повтор отправляет ту же цель и исходное время, но абсолютную гарантию exactly-once внешнее API не предоставляет. При спорных дублях проверять загрузки в Метрике.
- 14 ноября 2026 Метрика работает в ограниченном режиме: окно дополнения визитов из Директа — 10 дней, остальных источников — 3 дня. Сроки могут измениться. Статус `uploaded` не гарантирует попадание события в это окно.
